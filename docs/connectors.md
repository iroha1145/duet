# Official MCP connectors and native installations

This document describes the local implementation. The Gmail MCP candidate is frozen in `testing/gmail-mcp-race-fixed-frozen/sha256.json`; older installation evidence remains in `testing/connector-installs-frozen/sha256.json`. This change has not been deployed. Local implementation, local review, live deployment and actual provider consent are separate evidence.

The bridge uses official MCP services independently of Anthropic accounts. It never reads credentials from Codex, browser profiles or other apps. The current reviewed catalog contains GitHub, Hugging Face, Exa and Gmail. The user's scope permits official MCP replacements and skipping services without an official MCP. Additional services need an explicit reviewed adapter/catalog entry; arbitrary URLs are not accepted.

## Registration, settings and discovery

`register_connectors(app, data_dir, engine=...)` registers authenticated admin APIs and binds the manager to the engine. Account mode also calls `register_native_connectors(...)` before the catch-all. Saving configuration does not discover tools; explicit refresh initializes MCP and lists actual tools. Startup discovers persisted enabled installations. No enabled configuration means no MCP discovery traffic. A connection is not marked connected before initialization/tool discovery succeeds.

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/duet/connectors` | Sanitized catalog, installation configuration and connection status |
| PUT | `/duet/connectors/{id}` | Save one installation; revoke its old binding; no discovery |
| POST | `/duet/connectors/{id}/refresh` | Initialize and discover actual tools |
| POST | `/duet/connectors/{id}/disconnect` | Disable and revoke local tools/credentials |
| DELETE | `/duet/connectors/{id}` | Remove that installation |
| GET / PUT | `/duet/connector-oauth/{catalog}` | Inspect/configure owner-controlled OAuth settings; never return client secret |

Configuration includes `catalog_id, enabled, auth_type, token, readonly, timeout_seconds, additional_install, label`. There are at most eight installations total. IDs are stable, 1–24 lowercase letters/digits/underscores beginning with a letter. Omitted token preserves it; an empty token erases it. Public metadata exposes `token_set`, not the token. `connectors.json` and the OAuth SQLite database are private credential-bearing files, not a secret vault; POSIX directory/file modes request 0700/0600, with different Windows semantics.

| Service | Official MCP endpoint | Implemented authentication choices |
| --- | --- | --- |
| GitHub | `https://api.githubcopilot.com/mcp/` | Bearer PAT/access token; owner-configured browser OAuth; optional readonly header |
| Hugging Face | `https://huggingface.co/mcp` | Bearer token or explicitly configured browser OAuth |
| Exa | `https://mcp.exa.ai/mcp` | Explicit keyless/API-key modes or explicitly configured browser OAuth |
| Gmail | `https://gmailmcp.googleapis.com/mcp/v1` | Owner pre-registered AI agent OAuth web client only; draft saving, no sending |

Browser OAuth is implemented. It is disabled by default and requires a public HTTPS origin plus deliberate owner settings. GitHub requires the owner's pre-registered OAuth application; HF/Exa support configured `pre_registered`, `dcr` or `cimd` modes subject to discovery/validation. DCR is not performed merely by reading settings or listing the catalog. Missing credentials/disabled flow produce explicit status/errors, not fake connections. Provider availability and consent still require actual provider verification.

## Gmail setup and draft boundary

The official Gmail MCP is in Developer Preview. The owner must have Workspace Developer Preview access, enable `gmail.googleapis.com` and `gmailmcp.googleapis.com` in their Google Cloud project, configure consent/test users, and create a Web application OAuth client marked **Use this client for an AI-powered agent**. Register the exact bridge callback `https://YOUR_PUBLIC_ORIGIN/duet/oauth/callback/gmail`; Claude/Antigravity callback URLs are not this bridge's callback. See [Google's setup guide](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server).

In the existing authenticated connector settings, configure Gmail `registration_mode=pre_registered`, the owner's client ID and client secret, and explicitly enable OAuth. Install Gmail through the normal Connections directory and sign in through the normal external browser flow. No Google application, account or consent is created automatically. No provider credentials are included in the APK or copied from official Duet/Claude plugins. Gmail does not accept manually supplied bearer tokens, keyless access, DCR or CIMD in this implementation.

Default requested scopes are `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.compose`, as documented by Google. Configuration allows only those scopes plus optional `https://www.googleapis.com/auth/gmail.labels`; subsets are accepted and tools can fail if the user omits required permissions. Broad `mail.google.com`, `gmail.modify`, `gmail.send` and arbitrary scopes are refused. **`gmail.compose` itself grants Google-level sending authority**; the token is not inherently draft-only. The bridge restricts its usable MCP tools to draft creation, message/thread retrieval, draft/label listing, search, and labeling/unlabeling. Unknown future tools and send tools are removed before native publication and permission registration. Actual names, descriptions and schemas still come from MCP `tools/list`, never invented tool schemas. Google's label operations can require scopes outside this configured subset; no automatic widening occurs.

`create_draft` goes through ordinary engine approval and per-installation permissions, and returns the actual MCP result. A saved draft is **not** a sent email or `mailSent` success. This connector does not implement Gmail REST calls, `nativeSend`, a mail sender adapter, or a draft-card status conversion. Sending must be performed by the user in Gmail. See [the official tool reference](https://developers.google.com/workspace/gmail/api/reference/mcp) and [create_draft authorization and behavior](https://developers.google.com/workspace/gmail/api/reference/mcp/tools_list/create_draft).

Discovery pins [Gmail protected-resource metadata](https://gmailmcp.googleapis.com/.well-known/oauth-protected-resource/mcp/v1) and [Google OIDC metadata](https://accounts.google.com/.well-known/openid-configuration). Only this reviewed Google profile accepts the resource issuer `https://accounts.google.com/` while requiring OIDC/callback issuer `https://accounts.google.com`. Endpoint pinning, PKCE S256, state, owner/device binding, generation checks, completion tickets and refresh protection remain in force. Authorization requests add `access_type=offline` and `prompt=consent` for refresh-token consent.

Google's revocation can invalidate all tokens/scopes for the same Google user and Cloud project, across clients. The bridge therefore performs only local removal when another current Gmail grant uses the same OAuth client, or another enabled Gmail installation can still authorize under the same current client settings. This protection includes independently consented grants, without trying to identify the Google user. Removed token material is erased from grants and the retry queue; it is not retained for deferred revocation. Its Google grant can remain valid until last-install provider revocation or manual revocation in Google. The last active installation can revoke using its own single refresh token (or access token if no refresh token exists). Failed attempted remote revocation remains queued after local tools/grants are removed. A dedicated Google project/client limits effects on external integrations; bridge withholding cannot protect clients outside its catalog/store. See [Google token revocation semantics](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke).

A Gmail client-level lock covers the current-state revocation decision and entire remote request. The same lock covers authorization-code exchange through durable grant commit, and refresh exchange through durable rotation commit. A new local consent/refresh therefore cannot issue or publish tokens while an old last-install revocation is in flight. Installation/group locks precede this provider lock; revocation does not acquire those locks or the manager lock, and cleanup runs after token paths release the provider lock. Cancellation/failure releases the lock and retains queued revocation for a later current-state recheck. This is local coordination, not a guarantee about a provider completing a timed-out/cancelled request later or activity in external applications/processes.

## Native installation and OAuth flow

Both ordinary and `/api` native route prefixes are registered: directory listing, POST `organizations/{org}/mcp/remote_servers`, GET `.../start-auth/{server}`, DELETE `.../remote_servers/{server}`, POST `.../logout/{server}`, GET `mcp/auth_callback`, and PATCH `account/settings`.

Native `additional_install:true` creates a distinct installation for the same catalog entry, with a distinct stable server UUID and label. A normal install reuses the catalog's persisted primary installation. Migration preserves existing legacy IDs, UUIDs, tools and credentials; it does not rename existing accounts to a newly generated installation. Bootstrap lists installed entries, including disconnected/disabled entries with truthful status and empty tools, and emits `server_list`, `server_base`, `tools`, `completed`. Actual tool names use the installation namespace, for example `mcp__installation_id__remote_tool`.

The original Android browser launch/completion path is retained. PKCE, state, issuer, settings revision, installation generation, account/organization/device and redirect bindings are checked. Only the exact catalog callback and client-metadata GET paths are public. Provider authorization codes are exchanged server-side; authenticated polling returns a single-use completion ticket. Native `mcp/auth_callback` consumes that ticket, not a provider code. No provider token is handed to the APK.

Explicit `adopt_from=<server UUID>` selects an existing compatible grant for another installation. `share_grant_with=<server UUID>` selects targets during a new authorization; it cannot be combined with `adopt_from`, and there is at most one adoption source. Sharing is never an automatic fallback after login failure. Targets must be distinct compatible installations of the same catalog, with valid matching owner/binding/generation/redirect, no existing grant, and unchanged consent state. Settings/client/issuer/discovery/scopes must still agree when committed. At most seven share targets accompany the source. Arbitrary cross-account, cross-provider or stale selection is refused; nonempty attestations remain unsupported.

## Grant groups, permissions and removal

Explicitly shared grants form a group. Refresh is serialized by grant group, so members do not race the same rotating refresh token. Before dispatching refresh, all members are durably marked invalid/`refresh_uncertain`. A lost response, cancellation or process death can mean the one-use refresh token was spent; uncertain refresh is not replayed automatically. Successful rotation updates the still-current group atomically. Concurrent generation/configuration changes cannot overwrite a replacement installation's grant.

Grant sharing does not share tool permissions or approve calls. Each installation retains its own versioned tool-permission keys and enabled/always-approved choices. Adoption resets the destination's OAuth permissions. Deleting/disconnecting one installation immediately revokes its local tools, transactions and grant; it does not erase a sibling's independent permission state. Pending provider revocation is withheld while another current installation still uses the shared grant/token, and failures may remain in a private retry queue. This local guarantee does not promise a provider supports remote revocation: advertised provider capabilities determine that boundary.

## Execution and transport boundaries

The engine snapshots tool schemas and handlers together for an entire model turn. Credential/config/schema changes revoke old bindings instead of silently switching the account under an existing approval. Every remote call still passes the engine's approval and current versioned connector permission checks; standing Never/blocked policies win. The manager checks again after OAuth refresh and immediately before transport dispatch. Discovery, connection, grant adoption and metadata listing never approve business execution.

Streamable HTTP supports initialize/initialized, paginated tools/list and tools/call, bounded JSON/SSE, ping and session/protocol headers. Negotiated versions are 2025-11-25, 2025-06-18 and 2025-03-26. Server instructions/tool output are untrusted. Task-required tools are excluded because task augmentation was not negotiated. No automatic tools/call retry, event replay or reconnection/resumption is performed; an external operation may already have happened when its response is lost.

Redirects, cookies, ambient proxy credentials and URL credentials are disabled. HTTPS is required apart from an explicit loopback-only test option. Existing bounds are 1 MiB response/tool-list, 256 KiB tool results, 64 KiB schema, 128 tools and 20 pages. Known configured secrets/session IDs are redacted; this does not guarantee removal of arbitrary third-party secrets.

## Evidence and remaining scope

Older installation evidence recorded 15 installation/group cases and 63 legacy cases passing, with one Windows POSIX-mode skip; independent review closed three targeted fault scenarios. The Gmail candidate's exact source/test hashes and fresh loopback results are recorded in `testing/gmail-mcp-race-fixed-frozen/sha256.json` and `testing/gmail-mcp-race-fixed-frozen/results.txt`. The test scope includes Gmail's OAuth configuration, pinned discovery, PKCE/offline consent, completion tickets, exact tool filtering, normal engine approval/blocked policy, refresh, logout/retry, multiple installations and custom labels, plus the existing connector regression suites.

Actual Gmail/provider browser consent, Google preview entitlement, additional-install Android interactions and real multi-account provider behavior remain unverified for this candidate. Only unauthenticated official metadata/document lookups and local synthetic HTTP servers were used for Gmail. An earlier public Exa search is not proof of user authorization or group rotation. MCP prompts/resources, sampling, elicitation, subscriptions, task augmentation, legacy HTTP+SSE and arbitrary remote/stdio servers are not implemented. A provider requiring elicitation will fail safely rather than bypass confirmation. Retaining a native entry or disabling an unsupported gate does not establish full original-feature parity.
